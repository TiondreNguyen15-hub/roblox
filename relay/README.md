# Published Roblox → Render → Windows Player Data API

This integration runs in published Roblox servers and the normal Roblox desktop client. Studio is not the transport: authorized game servers POST to a public HTTPS Render relay; the separate Windows application polls that relay using a paired viewer credential. No process injection, Roblox memory reading, localhost requests from live servers, or publisher secrets in the desktop app are required.

## Deploy to Render

1. In Render, create a Blueprint from this GitHub repository. The root `render.yaml` selects the `relay` directory, Node 24, `node server.js`, and `/health`.
2. The Blueprint sets `ROBLOX_UNIVERSE_ID=10353139110`, using the Universe ID supplied for this task. It remains editable in Render environment settings. Verify this is the experience's **Universe ID**, not an individual Place ID. The service refuses to start without a valid numeric ID. Find it in Creator Hub for your experience.
3. Render generates `GAME_PUBLISH_TOKEN`. Keep it secret. Copy it directly from Render's environment settings into the Roblox Creator Hub secret described below, never into chat, source, desktop settings, or a LocalScript. Do not regenerate it without updating Roblox too.
4. Deploy and note the service's public HTTPS origin, for example `https://your-service.onrender.com`. Visit `/health` and expect `{"ok":true}`. This proves relay startup only, not game connectivity.
5. Use a **single service instance**. This version keeps pairing/session state in memory. Deployments, restarts, or instance replacement require re-pairing. Do not enable horizontal autoscaling without replacing session/token storage with a shared durable store.

An always-on Render instance is preferable for live use. Free-instance sleep/cold starts can exceed HTTP timeouts; Roblox and desktop retries recover when the service wakes, but live latency is not guaranteed. Render terminates TLS; the application binds its HTTP listener to Render's provided `PORT`. Do not expose the container's HTTP port directly on the public internet.

No deployment credentials are needed in this repository. No actual Render service has been created or deployed by this change.

## Configure and publish your Roblox experience

1. Install/update all folders from `game-tracker` in the matching services, or open the regenerated Studio demo and copy its PlayerTracking folders. Both new server modules and the new DesktopBridge LocalScript are required.
2. In `ReplicatedStorage.PlayerTracking.Config`, add authorized viewer UserIds to `AllowedUserIds`. The individual experience creator is allowed by default. Group-owned experiences need an explicit allowlist. Keep `AllowAllViewers=false` unless every player is meant to receive all tracking information.
3. In **Creator Hub → your experience → Secrets**, create `PLAYER_DATA_PUBLISH_TOKEN` using the value generated by Render. Restrict the secret to your exact relay hostname, such as `your-service.onrender.com`. The server obtains this with `HttpService:GetSecret` and supplies it only as an HTTPS Authorization header.
4. Enable **Allow HTTP Requests** for the experience. In the server-only `ExportConfig` ModuleScript, set `RelayUrl` to the HTTPS origin without a trailing slash and `Enabled=true`. Keep the secret's *name* in config, never its value.
5. Publish the updated place. Join a **new live server** in the normal Roblox desktop client; existing running servers do not receive edited scripts automatically. Your place must belong to the Universe ID configured in Render.
6. An authorized player with a spawned character will see a private 16-character pairing code at the top of their game window. It expires after ten minutes or one use. Codes are sent via FireClient, never public attributes. Unauthorized users receive neither camera export access nor a pairing code.

`StreamSkeleton=true` is required to export skeleton joints. The publisher sends one batch for all viewers at 2 Hz by default, independently of 10 Hz in-game tracking. This is 120 HTTP requests/minute per server, within Roblox's typical 500/minute server budget before other game HTTP use. Up to 10 viewers are included by default. Configure rates/viewer limits to leave budget for your own game. Network latency and HTTP batching mean this is not a frame-perfect screen-overlay feed.

## Pair the Windows app

1. Download the rebuilt Windows app. Expand **Profile & secure pairing** in its sidebar, enter the Render HTTPS origin and the in-game pairing code. Press **Pair game**.
2. The pairing result grants access only to that viewer in the configured universe. The native Electron main process saves the credential encrypted through Electron safeStorage (Windows OS encryption). It is not exposed to page scripts or stored in localStorage. Pairing is refused when OS encryption is unavailable.
3. The desktop polls at about 2 Hz and retries with exponential backoff up to 15 seconds. After initial pairing, fresh authenticated heartbeats detect the current place/server automatically, including rejoining another server in the same universe. This is authenticated game detection, not guessing from process names.
4. ESP switches to actual API visualization only after a valid fresh packet arrives. It draws server-derived boxes, names, distance in studs, health bars, team identifiers, skeletons, and a camera-oriented radar. Existing toggles are preserved; additional ESP toggles use the same layout. The black/blue styling and branding are retained in the dedicated ESP/Aimbot layout.
5. Missing/invalid/stale data clears visualization and displays a status instead of inventing players. Stop/re-pair using **Forget Pairing**. This revokes the server token when reachable and deletes the encrypted local credential. If offline, the server token remains valid until its 24-hour expiry.

The latest two-tab rebuild removes capture/ONNX previews and dependencies completely. ESP is API-only and shows an honest waiting/idle state until a validated matched feed arrives. Aimbot provides an authorized target selector/marker, not gameplay input automation. No fake data is used by production code; fixtures appear only in tests.

## API contract, version 1

| Endpoint | Authorization | Purpose |
| --- | --- | --- |
| GET /health | None | Basic health; no player information |
| POST /v1/publish | Bearer GAME_PUBLISH_TOKEN | Validated game snapshot; returns unpaired viewers' private codes to the publisher |
| POST /v1/pair | One-time code in JSON `code` | Returns viewer-scoped random bearer token |
| GET /v1/session | Viewer bearer token | Current paired game's data or `waiting` when stale |
| DELETE /v1/session | Viewer bearer token | Revoke that pairing |

Connected responses include `version`, `sequence`, `game` (`universeId`, `placeId`, `jobId`), `viewerUserId`, `connectedCount`, `camera`, and `players`. Player records contain `userId`, `username`, `displayName`, `position` XYZ, `rotation` row-major 3×3, `box` CFrame's 12 components, `size` XYZ, `health`, `maxHealth`, `teamId`, `rig`, and `joints` (part name → world XYZ). Roblox Teams have no inherent numeric team ID: set a custom `TeamId` attribute on each Team or the Team name is used. Neutral players use `Neutral`.

The count includes all connected players; world-space records require a spawned Humanoid/RootPart. Loading players and characters without a root have no fabricated location. A pairing viewer currently needs a spawned character as well.

Camera data is specific to the authorized viewing client: `cframe` is Roblox's 12-component CFrame; `viewport` is width/height; `fov` is normalized vertical degrees. It is sent through a rate-limited, type-checked RemoteEvent. Only camera fields come from the client; player position/health/team/joints come from the server. The server cannot authoritatively observe a client's camera, so camera correctness depends on that viewer. Projection uses Roblox's right-handed camera convention with negative local Z forward. Near-plane-crossing boxes are hidden. Radar uses horizontal positions, not screen-space guesses.

## Security and operating limits

- Publishing requires a 32+ character credential and the configured universe. Player/camera payloads are validated and limited to 2 MB, 500 character records, and 20 viewers per request.
- Pairing codes contain 64 bits of randomness, expire in ten minutes, and are single-use. Pair attempts are rate-limited to ten/minute per socket address; a reverse proxy may make this a shared limit. Tokens are random 256-bit values, hashed in relay memory, viewer-scoped, and expire after 24 hours.
- Responses use no-store. The relay does not enable browser CORS and does not log player snapshots or secrets. HTTPS redirects are rejected by the desktop to avoid forwarding credentials elsewhere.
- Old sequences cannot refresh a same-server feed. After five seconds without a publish, the relay returns `waiting` without player/camera data. Session memory expires after 30 minutes without game traffic.
- Keep a single Render instance. For larger/public deployments, add durable session storage, operational monitoring, per-credential publishing quotas, and explicit operator revocation/admin controls before scaling beyond this personal-experience deployment.

## Game Profile: Place 79862723087324

The desktop ships with one editable profile for Place ID `79862723087324`. Under Profile & secure pairing, edit Place ID/Profile name, press Save Game Profile, and use Save feature settings after connecting to save that profile's ESP/Aim control values. An uncustomized profile inherits existing settings rather than overwriting them. Profile configuration lives locally; it is not an API credential.

The separate `game-process.js` monitor queries only the Windows `RobloxPlayerBeta` process name every three seconds; it does not read Roblox memory, logs, cookies, or command-line credentials. The separate `game-profiles.js` registry matches authenticated API `game.placeId` values, loads matching settings, and displays the game name reported by the Roblox server's MarketplaceService. If the name lookup fails, it says Name unavailable rather than making up a detected name. Process launch alone displays Waiting for authorized Place ID. Without the published-game integration, the app cannot reliably identify the currently played experience.

A mismatched game does not activate the new Player Data ESP. Exiting Roblox or losing fresh API data clears the active visualization. A paired game server can reconnect automatically, but initial authorization/pairing is always explicit. The registry can be extended with more profile IDs/Place IDs and settings; the current Settings editor edits the first profile. Multiple universes require separately scoped relay credentials/configuration rather than trusting arbitrary games.

The Universe ID `10353139110` and Place ID `79862723087324` were supplied separately. Their relationship has not been verified against Roblox here; confirm both in Creator Hub. The relay rejects snapshots from a different universe. Windows native process detection and published-game naming/identity remain live-test requirements; browser regression tests used explicitly labeled protocol fixtures.

## Current LAUNCH/STOP interface

The current desktop has only ESP and Aimbot tabs. Pair once, then press LAUNCH; the native controller initializes the authorized integration automatically. It remains armed through game exit/reopen and switches supported profiles on authenticated game identity changes. STOP cancels requests/rendering and disarms auto-start while retaining the encrypted credential. No capture or ONNX fallback remains.
